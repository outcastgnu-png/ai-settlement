## Form answers

1. What they build: AgentTrust, an XRPL escrow and verification service for agent jobs (a
   peer project).
2. Language / OS: Python SDK on Linux (Debian; Python 3.13.5, Node 24.22.1).
3. Setup minutes: about 1.
4. Where they got stuck: no blockers. One mismatch: the v0.3.0 tag (0c4b66c) predates
   7cd2bf0 ("Tighten the trial kit..."), so a v0.3.1 tag would let testers run exactly what
   the current script describes.
5. Paid job / refunded job: yes / yes.
6. Explorer link: see the Run table.
7. Confusing or missing in the SDK: `claim()` and `refund()` return `TxOutcome(tx, job)`,
   but the README said jobs come back as dicts, so `.get("status")` raised `AttributeError`
   after a successful claim. The positional `create_job(client, provider, "2000000", 300, spec)`
   deserves keyword names. The README didn't document the `deliver()` result fields.
8. Trust in the signed verdict: enough for deterministic checks (sha256, json-schema,
   latency), since the SDK verifies the verdict against the pinned `ORACLE_VERDICT_ADDRESS`
   and the ledger enforces the condition. The remaining trust is in the single oracle
   operator, as THREAT_MODEL says. For real funds they'd want a public verdict log or a
   second oracle.
9. A real job they would escrow: paying another agent for a short research answer
   delivered as JSON with sources, released only if the structure is right and it arrives on
   time (the json-schema + max-latency pair they tested).
10. Missing check: anything about quality, meaning whether the answer is correct and
    on-topic; json-schema checks structure only. An "XRPL tx exists and is validated" check
    would also be cheap and useful.
11. Self-hosted vs hosted: hosted for small teams, priced per check rather than monthly
    (for reference, AgentTrust charges $0.10 per AI check).
12. Anything else: clean kit, and the 403 for a client asking for the provider's
    fulfillment was a nice touch.
